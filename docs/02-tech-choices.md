# ۲. انتخاب تکنولوژی‌ها — چه، چرا، چگونه

برای هر تکنولوژی این سند به سه سوال پاسخ می‌دهد: **چه** ابزاری انتخاب شده؟ **چرا** این ابزار به جای جایگزین‌ها؟ و **چگونه** در این پروژه استفاده شده است؟

معیار اصلی در همه تصمیم‌ها: **مقیاس واقعی مسئله**. این سیستم باید ~۵۰۰ صندوق با داده روزانه (و برای صندوق‌های سهامی، داده هر دقیقه در ساعات معاملات) را پوشش دهد — یعنی حدود چند هزار ردیف در روز. این مقیاس «متوسط رو به پایین» است؛ بنابراین ابزاری انتخاب شده که این مقیاس را با حاشیه اطمینان بالا پوشش دهد، بدون اینکه هزینه عملیاتی (راه‌اندازی، دیباگ، نیروی انسانی) تحمیل کند.

---

## ۲.۱ زبان و وب‌فریمورک

### Python 3.11

- **چه:** زبان اصلی سرویس (backend و worker).
- **چرا:** اکوسیستم استاندارد صنعت کوانت و مهندسی داده (`pandas`/`numpy`/`polars`، کتابخانه‌های مالی، ابزارهای ETL). شرح شغل نیز دقیقاً همین را می‌خواهد. نسخه 3.11 برای بهبود کارایی (`__slots__`، اجرای سریع‌تر) و سازگاری کامل با کتابخانه‌ها انتخاب شد.
- **چگونه:** کل backend، توابع محاسبات مالی خالص، و وظایف زمان‌بندی‌شده.

### FastAPI + Uvicorn

- **چه:** فریم‌ورک وب async با تایپ‌هینت اجباری.
- **چرا:** (۱) تایپ‌هینت اجباری = خودمستندسازی و کاهش باگ؛ (۲) مستندات OpenAPI/Swagger خودکار روی `/docs` — بدون تلاش اضافه؛ (۳) عملکرد بالا برای JSON API؛ (۴) سادگی نسبت به Django (که ORM و ادمینش برای این پروژه اضافه‌بار است) و بلوغ بیشتر نسبت به Flask برای APIهای تایپ‌شده.
- **چگونه:** روتر واحد `routers/web.py` شامل صفحات SSR و APIهای JSON تحلیلی. Health check اختصاصی روی `/health` برای Docker.

## ۲.۲ پایگاه داده و ذخیره‌سازی

### PostgreSQL 15

- **چه:** دیتابیس اصلی و «منبع حقیقت» (Source of Truth) کل سیستم.
- **چرا — و نه MongoDB؟** داده این پروژه **رابطه‌ای** است: صندوق → تاریخچه، ETF → تاریخچه، صندوق ↔ ETF. یکپارچگی ارجاعی (FK)، قیود یکتایی و JOINهای تحلیلی دقیقاً کاری است که SQL برایش ساخته شده؛ MongoDB برای اسناد ناهمگن مناسب است و در اینجا فقط دردسر تکراری‌سازی داده اضافه می‌کرد.
- **چرا — و نه ClickHouse یا دیتابیس سری زمانی (TimescaleDB/InfluxDB)؟** این سوال در مصاحبه حتماً پرسیده می‌شود. پاسخ: دیتابیس‌های سری زمانی زمانی توجیه دارند که (۱) حجم رکورد در روز میلیونی باشد، (۲) دقت میلی‌ثانیه‌ای tick لازم باشد، یا (۳) نگهداری چندساله raw data مطرح باشد. این پروژه چند هزار ردیف در روز تولید می‌کند و تحلیل‌ها به JOIN با متادیتای صندوق نیاز دارند (که در دیتابیس‌های ستونی ضعیف است). PostgreSQL در این مقیاس هم ساده‌تر است هم سریع‌تر از نیاز. **اگر** قرار بود tick-by-tick کل بازار (نه صندوق‌ها) ذخیره شود، انتخاب TimescaleDB یا ClickHouse بود — و این استدلال مقیاس‌محور در سند معماری صریح شده است.
- **چگونه:** upsertهای اتمیک با `INSERT ... ON CONFLICT DO UPDATE` بومی (نه read-modify-write که شرط مسابقه دارد)، قید یکتایی `(fund_reg_no, observed_at)` برای ایدمپوتنسی، ایندکس‌های ترکیبی در `migrations/001`.

### Redis 7

- **چه:** کش توزیع‌شده + (آینده) صف وظایف.
- **چرا:** وب و worker دو فرآیند جدا هستند؛ کش درون‌حافظه‌ای هرکدام با دیگری ناسازگار می‌شد (وب باید بداند چه زمانی worker داده را تازه کرد). Redis یک نقطه هماهنگی مشترک است. `fastapi-cache2` با بک‌اند Redis این را استاندارد حل می‌کند.
- **چگونه:** کش پاسخ endpointهای تحلیلی سنگین داشبورد؛ پس از هر سینک موفق، worker کش را invalidate می‌کند (`cache_service.py`) تا داده تازه به کاربر برسد.

## ۲.۳ زمان‌بندی و جمع‌آوری داده

### APScheduler (در فرآیند worker جدا)

- **چه:** زمان‌بندی وظایف داخل `worker.py` با `BlockingScheduler`.
- **چرا — و نه Celery؟** Celery برای صف‌های توزیع‌شده با هزاران وظیفه و retry پیشرفته ساخته شده؛ این پروژه **۳ وظیفه دوره‌ای** دارد (سینک صندوق، سینک ETF، بک‌فیل). اضافه کردن broker اختصاصی (RabbitMQ/Redis)، worker های celery و زیرساخت مانیتورینگ آن، هزینه عملیاتی را چند برابر می‌کرد بدون هیچ سود واقعی. انتخاب آگاهانه: «ساده‌ترین ابزاری که مسئله را حل می‌کند». اگر تعداد وظایف به ده‌ها رسید، مهاجرت به Celery یک تغییر محلی در worker است.
- **چگونه:** سه job با `max_instances=1` (جلوگیری از اجرای هم‌زمان یک وظیفه)، `coalesce=True` (اگر اجرا عقب افتاد، اجراهای انباشته را یکی کند) و `misfire_grace_time` منطقی.

### requests + retry سفارشی

- **چه:** کلاینت HTTP به TSETMC با retry و backoff.
- **چرا — و نه httpx/aiohttp؟** نقطه گلوگاه واقعی API خارجی است (نه تعداد درخواست‌های هم‌زمان ما)؛ async بودن در اینجا سود قابل اندازه‌گیری ندارد و همگام بودن، دیباگ خط لوله را ساده می‌کند. `requests` پایدارترین انتخاب است.
- **چگونه:** `request_with_retry` با چند تلاش برای خطاهای گذرا، timeout صریح، و ایزوله‌سازی endpointهای ناپایدار TSETMC (که 500 می‌دهند) تا خطای منبع، کل مدار را مسموم نکند (درس گرفته‌شده در فاز ۷ سند ۶).

## ۲.۴ لایه داده (ORM)

### SQLAlchemy 2.0

- **چه:** ORM برای تعریف مدل‌ها و کوئری‌ها.
- **چرا:** کنترل دقیق روی SQL تولیدی، پشتیبانی کامل از `INSERT ... ON CONFLICT` بومی Postgres، و maturity. (در این مقیاس، ORMهای سبک‌تر مثل Tortoise یا نوشتن SQL خام هیچ‌کدام ترکیب «امنیت تایپ + کنترل» را نمی‌دهند.)
- **چگونه:** مدل‌های declarative در `core/models.py`؛ کوئری‌های تحلیلی (aggregation، join سه‌طرفه برای انتخاب صندوق‌های ناقص) مستقیماً با Query API.

### python-dateutil

- **چه:** پارس مقاوم تاریخ.
- **چرا:** TSETMC تاریخ‌ها را در دو قالب متفاوت برمی‌گرداند: ISO (`"2012-09-23T00:00:00"` برای تاریخچه صندوق) و `YYYYMMDD` عددی (`dEven` برای قیمت ETF). یک پارسر واحد باید هر دو را بفهمد (این دقیقاً همان باگی بود که در فاز ۸ سند ۶ رفع شد).
- **چگونه:** `parse_tsetmc_date` در `history_bootstrap.py`: ابتدا قالب ۸ رقمی، سپس `dateutil.parser.parse`، و خروجی همیشه naive datetime (بدون timezone) برای سازگاری با ستون `TIMESTAMP`.

## ۲.۵ لایه ارائه

### Jinja2 (Server-Side Rendering) + Bootstrap 5 RTL

- **چه:** صفحات HTML در سمت سرور رندر می‌شوند.
- **چرا — و نه React/Vue (SPA)؟** این داشبورد یک ابزار مانیتورینگ داخلی است، نه محصول چندصفحه‌ای با تعامل پیچیده. SPA یعنی: build step جدا، state management، routing سمت کلاینت، و دو برابر شدن سطح حمله باگ — برای سودی که در این مقیاس وجود ندارد. SSR با Jinja بار اولیه را سریع تحویل می‌دهد و SEO/اشتراک‌گذاری لینک را ساده نگه می‌دارد. انتخاب آگاهانه بر اساس «سادگی که مقیاس را جواب می‌دهد».
- **چگونه:** `templates/base.html` (RTL، نوار ناوبری) + قالب‌های هر صفحه؛ داده‌های زنده با fetch سمت کلاینت به APIهای JSON.

### Chart.js + Highcharts

- **چه:** دو کتابخانه نمودار سمت کلاینت.
- **چرا:** Chart.js برای نمودارهای خطی/میله‌ای (NAV، مقایسه) — سبک و ساده؛ Highcharts برای **Treemap/Heatmap** نقشه حرارتی بازار — چون treemap با رنگ‌بندی پویا در Chart.js موجود نیست و این نمودار قلب «تصویر بزرگ» داشبورد است.
- **چگونه:** هر دو از CDN بارگذاری می‌شوند؛ داده از APIهای JSON (`/api/dashboard/heatmap` و ...) گرفته می‌شود.

## ۲.۶ زیرساخت و کیفیت

### Docker + Docker Compose

- **چه:** چهار سرویس (web، worker، db، redis) با build چندمرحله‌ای و healthcheck.
- **چرا:** شرط صریح تسک («مستقیماً روی هر محیطی قابل اجرا»). Compose ساده‌ترین راه برای تعریف توپولوژی و وابستگی‌ها (`depends_on: condition: service_healthy`) است. در محیط تولیدی، همین فایل با کمی تغییر به Kubernetes منتقل می‌شود (شرح شغل آشنایی با K8s را می‌خواهد).
- **چگونه:** healthcheck واقعی (pg_isready برای db، درخواست به `/health` برای web)، named volumes برای پایداری داده، سیاست‌های `restart: unless-stopped`، `.dockerignore` برای تصویر تمیز.

### pytest (۴۵ آزمون)

- **چه:** چارچوب تست با سه لایه: unit (فرمول‌های مالی)، integration (API با دیتابیس in-memory)، regression (باگ‌های رفع‌شده).
- **چرا:** فرمول‌های مالی باید اثبات‌پذیر درست باشند؛ خط لوله داده باید در برابر داده کثیف مقاوم باشد. تست‌ها همچنین نقش «حافظه باگ‌ها» را دارند (نگاه کنید به `test_history_bootstrap.py` — هر باگ رفع‌شده یک تست دائمی دارد).
- **چگونه:** SQLite in-memory با StaticPool برای تست‌های دیتابیس (بدون نیاز به Postgres واقعی)، mocking برای Provider خارجی.
