# ۲. انتخاب تکنولوژی‌ها

برای هر انتخاب اینجا گفته‌ام چه گرفتم، چرا، و جایگزین‌هایی که کنار گذاشتم.

معیار همه تصمیم‌ها یک چیز بوده: **مقیاس واقعی مسئله.** این سیستم حدود ۵۰۰ صندوق با داده روزانه دارد، و برای صندوق‌های سهامی داده هر دقیقه در ساعات معاملات — یعنی چند هزار ردیف در روز. این مقیاس «متوسط رو به پایین» است. پس ابزاری انتخاب کرده‌ام که این مقیاس را با حاشیه اطمینان بالا جواب بدهد، بدون اینکه هزینه عملیاتی (راه‌اندازی، دیباگ، نیروی انسانی) تحمیل کند. ابزار شیک برای مقیاس اشتباه، مهندسی نیست — خرید بدهی است.

## زبان و وب‌فریمورک

### Python 3.11

انتخابش بدیهی بود: اکوسیستم استاندارد کوانت و مهندسی داده (`pandas`/`numpy`، کتابخانه‌های مالی، ابزارهای ETL) و دقیقاً همان چیزی که شرح شغل می‌خواست. نسخه 3.11 را برای کارایی بهتر و سازگاری کامل با کتابخانه‌ها گرفتم.

### FastAPI + Uvicorn

تایپ‌هینت اجباری، مستندات Swagger خودکار روی `/docs` بدون هیچ تلاشی، و عملکرد بالا برای JSON API. در مقایسه با Django، ORM و ادمینش اینجا اضافه‌بار بود؛ در مقایسه با Flask، تایپینگ و اعتبارسنجی FastAPI برای یک API جدی مناسب‌تر است. روتر واحد `routers/web.py` هم صفحات SSR را دارد هم APIهای JSON تحلیلی را.

## دیتابیس و ذخیره‌سازی

### PostgreSQL 15

منبع حقیقت کل سیستم.

دو سوالی که معمولاً درباره این انتخاب مطرح می‌شود، و جوابم صریح است:

اول، **چرا MongoDB نه؟** چون داده این پروژه ذاتاً رابطه‌ای است: صندوق → تاریخچه، ETF → تاریخچه، صندوق ↔ ETF. یکپارچگی ارجاعی، قیود یکتایی و JOINهای تحلیلی دقیقاً کاری است که SQL برایش ساخته شده. MongoDB برای اسناد ناهمگن خوب است؛ اینجا فقط دردسر تکراری‌سازی داده اضافه می‌کرد.

دوم، **چرا ClickHouse یا دیتابیس سری زمانی نه؟** دیتابیس سری زمانی وقتی توجیه دارد که حجم رکورد روزانه میلیونی باشد، دقت میلی‌ثانیه‌ای tick لازم باشد، یا نگهداری چندساله raw data مطرح باشد. این پروژه چند هزار ردیف در روز تولید می‌کند و تحلیل‌هایش به JOIN با متادیتای صندوق نیاز دارند — دقیقاً جایی که دیتابیس‌های ستونی ضعیف‌اند. PostgreSQL در این مقیاس هم ساده‌تر است هم سریع‌تر از نیاز. اگر قرار بود tick-by-tick کل بازار را ذخیره کنم، TimescaleDB یا ClickHouse را انتخاب می‌کردم.

جزئیات استفاده: upsert اتمیک با `INSERT ... ON CONFLICT DO UPDATE` بومی (نه read-modify-write که شرط مسابقه دارد)، قید یکتایی `(fund_reg_no, observed_at)` برای ایدمپوتنسی، و ایندکس‌های ترکیبی در `migrations/001`.

### Redis 7

کش مشترک web و worker — دلیلش را در سند ۱ گفتم: بدون یک نقطه هماهنگی مشترک، web هیچ‌وقت نمی‌فهمد worker داده را تازه کرده. `fastapi-cache2` با بک‌اند Redis این را استاندارد حل می‌کند: پاسخ endpointهای تحلیلی سنگین کش می‌شود و بعد از هر سینک موفق، worker کش را invalidate می‌کند تا داده تازه به کاربر برسد. اگر بعداً صف وظایف لازم شد، Redis همان زیرساخت است.

## زمان‌بندی و جمع‌آوری داده

### APScheduler (در فرآیند worker جدا)

زمان‌بندی وظایف داخل `worker.py` با `BlockingScheduler`.

چرا Celery نه؟ Celery برای صف‌های توزیع‌شده با هزاران وظیفه و retry پیشرفته ساخته شده؛ این پروژه ۵ وظیفه دوره‌ای دارد. اضافه کردن broker اختصاصی (RabbitMQ/Redis)، worker های celery و زیرساخت مانیتورینگش، هزینه عملیاتی را چند برابر می‌کرد بدون هیچ سود واقعی. اگر روزی ده‌ها وظیفه داشتیم، مهاجرت به Celery یک تغییر محلی در worker است. سه job با `max_instances=1` (جلوگیری از اجرای هم‌زمان)، `coalesce=True` (ادغام اجراهای عقب‌افتاده) و `misfire_grace_time` منطقی تنظیم شده‌اند.

### requests (bulk) + httpx/asyncio (fan-out تکمیلی)

این انتخاب دو مرحله‌ای است و داستانش را دوست دارم، چون نشان می‌دهد ابزار باید از اندازه‌گیری بیاید، نه از پیش‌داوری.

تصمیم اولیه من فقط `requests` بود، با این استدلال که گلوگاه API خارجی است نه همزمانی ما — و تا وقتی هر چرخه چند درخواست bulk داشت، درست هم بود. اما فاز تکمیلی ETF ده‌ها درخواست پنج‌ثانیه‌ای را پشت‌سرهم می‌زد و یک چرخه واقعی حدود **۴۰ دقیقه** طول می‌کشید — در تضاد مستقیم با قرارداد «هر ۱ دقیقه» خود تابلوی ETF. این را از لاگ خود سیستم دیدم، نه از حدس. پس فقط همان فازی که واقعاً همزمانی لازم داشت عوض شد: درخواست‌های bulk روی `requests` ماندند (سادگی دیباگ)، فاز تکمیلی با `httpx.AsyncClient` و `asyncio.gather` همزمان شد — با `Semaphore(20)` به‌عنوان سقف همزمانی تا منبع داده له نشود، `return_exceptions=True` تا شکست هر ردیف ایزوله بماند، و `asyncio.run()` برای اجرای job چون `BlockingScheduler` در ThreadPoolExecutor نمی‌تواند coroutine اجرا کند. `request_with_retry` (برای bulk) هم با backoff، timeout صریح و ایزوله‌سازی endpointهای ناپایدار TSETMC کار می‌کند تا خطای منبع، کل مدار را مسموم نکند. نتیجه: چرخه کامل از ~۴۰ دقیقه به چند ثانیه. جزئیات بیشتر در فاز ۱۲ سند ۶.

## لایه داده (ORM)

### SQLAlchemy 2.0

برای تعریف مدل‌ها و کوئری‌ها. دلیل: کنترل دقیق روی SQL تولیدی، پشتیبانی کامل از `INSERT ... ON CONFLICT` بومی Postgres، و maturity. در این مقیاس، ORMهای سبک‌تر یا SQL خام هیچ‌کدام ترکیب «امنیت تایپ + کنترل» را نمی‌دهند. کوئری‌های تحلیلی (aggregation، join سه‌طرفه برای انتخاب صندوق‌های ناقص) مستقیم با Query API نوشته شده‌اند.

### python-dateutil

برای پارس مقاوم تاریخ. TSETMC تاریخ‌ها را در دو قالب متفاوت برمی‌گرداند: ISO (`"2012-09-23T00:00:00"` در تاریخچه صندوق) و `YYYYMMDD` عددی (`dEven` در قیمت ETF). این دوگانگی دقیقاً همان چیزی بود که یک باگ واقعی ساخت (فاز ۸ سند ۶): بک‌فیل هزاران رکورد را بی‌صدا دور می‌ریخت چون پارسر فقط یک قالب را می‌فهمید. حالا یک پارسر واحد (`parse_tsetmc_date` در `providers.py` — کنار منبع داده، چون شکل تاریخ جزئی از قرارداد provider است) هر دو قالب را می‌فهمد و خروجی‌اش همیشه naive datetime است.

## لایه ارائه

### Jinja2 (SSR) + Bootstrap 5 RTL

چرا React/Vue نه؟ این داشبورد یک ابزار مانیتورینگ داخلی است، نه محصول چندصفحه‌ای با تعامل پیچیده. SPA یعنی build step جدا، state management، routing سمت کلاینت و دو برابر شدن سطح حمله باگ — برای سودی که در این مقیاس وجود ندارد. SSR با Jinja بار اولیه را سریع تحویل می‌دهد و اشتراک‌گذاری لینک را ساده نگه می‌دارد. داده‌های زنده با fetch سمت کلاینت به APIهای JSON می‌آیند.

### Chart.js + Highcharts

Chart.js برای نمودارهای خطی/میله‌ای (NAV، مقایسه) — سبک و ساده. Highcharts فقط برای Treemap/Heatmap نقشه حرارتی بازار — چون treemap با رنگ‌بندی پویا در Chart.js موجود نیست و این نمودار قلب «تصویر بزرگ» داشبورد است.

دو درس عملیاتی از همین بخش که با مرورگر بی‌صدا (headless Chrome) پیدا شدند، نه با تست API: اول اینکه CDN رسمی Highcharts از بعضی شبکه‌ها (از جمله شبکه اجرای خود پروژه) 403 برمی‌گرداند — کنسول مرورگر `Highcharts is not defined` را لو داد در حالی که همه APIها سالم بودند؛ رفعش پین‌کردن `highcharts@13.0.2` از همان CDN ای که Chart.js از آن کار می‌کرد (`cdn.jsdelivr.net`) بود — پین‌کردن نسخه یعنی ارتقای ناخواسته ماژول‌ها (coloraxis/treemap) با هسته ناسازگار نمی‌شود. دوم اینکه Chart.js فقط روی عنصر `<canvas>` کار می‌کند — با div بدون هیچ خطایی هیچ‌چیز نمی‌کشد و متن «در حال دریافت اطلاعات» برای همیشه می‌ماند. نتیجه کلی: تست API کافی نیست؛ «صفحه رندر شده» فقط با مرورگر واقعی تضمین می‌شود.

## زیرساخت و کیفیت

### Docker + Docker Compose

چهار سرویس (web، worker، db، redis) با healthcheck واقعی و `.dockerignore` برای تصویر تمیز. این بخش شرط صریح تسک بود («مستقیماً روی هر محیطی قابل اجرا») و من آن را جدی‌تر از بقیه گرفتم: سیستم را با `docker compose down -v` از صفر تست کردم — دقیقاً همان کاری که ارزیاب می‌کند — و دو جای خالی پیدا کردم (اجرای خودکار مهاجرت‌ها و پیش‌فرض‌های `.env`) که بدون این تست، روز تحویل می‌ترکیدند. جزئیات در سند ۷.

### pytest (۱۰۶ آزمون)

سه لایه: unit (فرمول‌های مالی و قوانین اعتبارسنجی)، integration (API و خط لوله زنده با دیتابیس in-memory)، regression (باگ‌های رفع‌شده). فرمول‌های مالی باید اثبات‌پذیر درست باشند؛ خط لوله داده باید در برابر داده کثیف مقاوم باشد. تست‌ها «حافظه باگ‌ها» هستند — هر باگ مهمی که پیدا کردم، یک تست دائمی دارد (`test_history_bootstrap.py` را ببینید). برای دیتابیس تست‌ها از SQLite in-memory با StaticPool استفاده می‌کنم (بدون نیاز به Postgres واقعی) و Provider خارجی mock می‌شود.
