# ۱. معماری سیستم

## ۱.۱ نمای کلی

سیستم از چهار سرویس مستقل تشکیل شده که هرکدام در یک کانتینر جدا اجرا می‌شوند:

```
                         ┌────────────────────────────────────────┐
                         │              TSETMC API               │
                         │   (منبع رسمی داده بازار بورس ایران)     │
                         └──────────────┬─────────────────────────┘
                                        │ HTTPS (requests bulk + httpx async)
                         ┌──────────────▼─────────────────────────┐
                         │             worker (APScheduler)       │
                         │  • سینک زنده صندوق‌های سهامی (هر ۱ دقیقه)│
                         │  • تابلوی ETF زنده (هر ۱ دقیقه)         │
                         │  • بک‌فیل تاریخچه (بوت‌استرپ)           │
                         │  • سینک شاخص کل (هر ۱۵ دقیقه)           │
                         │  • جاروب اعتبارسنجی (هر ۱۵ دقیقه)       │
                         └───────┬───────────────────┬────────────┘
                                 │ SQLAlchemy        │
                    ┌────────────▼───────┐   ┌───────▼────────┐
                    │   PostgreSQL 15    │   │    Redis 7     │
                    │  (منبع حقیقت داده)  │   │ (کش + لایه داغ) │
                    └────────────▲───────┘   └───────▲────────┘
                                 │            invalidate │ cache
                    ┌────────────┴───────────────┐        │
                    │        web (FastAPI)       ├────────┘
                    │  • صفحات SSR (Jinja2)      │
                    │  • APIهای JSON تحلیلی      │
                    └────────────┬───────────────┘
                                 │ HTTP
                           ┌─────▼──────┐
                           │   مرورگر    │
                           │ Bootstrap  │
                           │ Chart.js + │
                           │ Highcharts │
                           └────────────┘
```

**چرا دو فرآیند جدا (`web` و `worker`)؟** جمع‌آوری داده و سرو کردن داده دو چرخه عمر متفاوت دارند: `worker` باید بدون وقفه برنامه‌ریزی شود (کرون‌جاب)، در حالی که `web` باید سبک و پاسخگو بماند. اگر هر دو در یک فرآیند بودند، یک درخواست API کند می‌توانست سینک داده را عقب بیندازد و بالعکس. این جداسازی همچنین اجازه می‌دهد هر جزء مستقل scale یا restart شود.

```

│   └── benchmark.py         ← پیکربندی شاخص‌های بازار (Benchmark)
├── services/                ← لایه منطق کسب‌وکار (پردازش)
│   ├── providers.py         ← الگوی Provider: کلاینت TSETMC (جداسازی منبع داده)
│   ├── preprocessing.py     ← پاک‌سازی و نرمال‌سازی داده خام
│   ├── fund_sync.py         ← خط لوله سینک زنده صندوق‌ها + اعتبارسنجی inline
│   ├── tasks.py             ← جمع‌آوری داده تابلوی ETF
│   ├── history_bootstrap.py ← بک‌فیل تاریخچه NAV با state tracking
│   ├── benchmark_sync.py    ← سینک افزایشی شاخص کل (TEDPIX)
│   ├── validation.py        ← قوانین خالص اعتبارسنجی صحت داده
│   ├── validation_sweep.py  ← جاروب دوره‌ای تاریخچه‌ها (outlier، شکاف، کهنگی)
│   ├── analytics.py         ← توابع بازدهی و نرمال‌سازی سری زمانی

│   ├── data_quality.py      ← امتیاز کیفیت و پوشش داده
```

## ۱.۳ الگوهای طراحی استفاده‌شده

### Repository Pattern (`core/repositories.py`)

**چه:** تمام دسترسی به دیتابیس — از upsert صندوق تا محاسبه معیارهای ریسک — در کلاس‌های Repository متمرکز شده است (`FundRepository`, `ETFRepository`, `BenchmarkRepository`).

**چرا:** سرویس‌ها و روترها هرگز SQL نمی‌نویسند؛ آن‌ها معنای عملیات را صدا می‌زنند (`repo.upsert_fund_history(...)`). نتیجه: کوئری‌ها یک نقطه تغییر دارند، در تست‌ها قابل mock هستند و منطق دامنه از جزئیات ذخیره‌سازی جدا می‌ماند (اگر فردا دیتابیس عوض شود، فقط Repository عوض می‌شود).

**چگونه:** هر Repository یک `db: Session` می‌گیرد و به ازای هر عملیات یک متد صریح دارد. برای عملیات حجیم، از `pg_insert` بومی PostgreSQL با `ON CONFLICT` استفاده می‌شود (upsert اتمیک بدون دور باطل read-modify-write).

### Provider Pattern (`services/providers.py`)

**چه:** کلاینت منبع داده (`TSETMCProvider`) تنها جایی است که از آدرس‌ها، فرمت‌ها و رفتارهای عجیب API خارجی خبر دارد. شامل retry با backoff و ایزوله‌سازی endpointهای ناپایدار است.

**چرا:** APIهای بیرونی (به‌ویژه TSETMC) ناپایدار و پر از موارد خاص هستند. با جداسازی این ناپایداری پشت یک Provider، بقیه سیستم همیشه با یک رابط تمیز و پایدار کار می‌کند. اگر فردا منبع داده دوم (مثلاً Platts یا QuantConnect — مطابق شرح شغل) اضافه شود، فقط یک Provider جدید نوشته می‌شود.

**چگونه:** متدهایی مانند `fetch_funds_by_type(type)`، `fetch_fund_history_detail(reg_no)`، `fetch_live_etf_prices()` و `fetch_etf_history(ins_code)` — هرکدام با timeout مشخص، retry برای خطاهای گذرا، و لاگ شفاف.

### Separation of Concerns بین سرویس‌ها

هر فایل در `services/` دقیقاً یک نگرانی را بر عهده دارد:

| سرویس | نگرانی | خروجی |
|---|---|---|
| `providers` | ارتباط با دنیای بیرون | دیکشنری خام |
| `preprocessing` | پاک‌سازی داده خام | دیکشنری تمیز |
| `fund_sync` / `tasks` | هماهنگی خط لوله | ردیف‌های دیتابیس + امتیاز کیفیت |
| `validation` / `validation_sweep` | اعتبارسنجی صحت داده و قرنطینه | تخلف‌های ثبت‌شده |
| `benchmark_sync` / `history_bootstrap` | تکمیل داده از منبع (شاخص و تاریخچه) | ردیف‌های جدید |
| `analytics` / `risk` / `etf_analytics` | محاسبات مالی خالص | عدد/لیست |
| `data_quality` | سنجش سلامت داده | امتیاز/پوشش |

محاسبات مالی (`analytics`, `risk`) و قوانین اعتبارسنجی (`validation`) **خالص** (pure) هستند: نه دیتابیس می‌بینند نه شبکه. به همین دلیل با کمترین تلاش تست شدند.

### Graceful Degradation و ایزوله‌سازی خطا

هر وظیفه زمان‌بندی‌شده در `worker.py` داخل `try/except` مستقل است: شکست یک سینک، سرویس را نمی‌کشد. Endpointهای ناپایدار TSETMC (که خطای 500 می‌دهند) از مسیر اصلی جدا شده‌اند تا «مدارشکن» کل سیستم را مسموم نکند؛ در صورت شکست، سیستم با آخرین داده معتبر به کار ادامه می‌دهد و صندوق موردنظر برای تلاش مجدد در صف می‌ماند (جدول `history_backfill_state`).

## ۱.۴ مدل داده (اسکیما)

| جدول | محتوا | کلید |
|---|---|---|
| `funds` | اطلاعات پایه و فوری صندوق (NAV، بازدهی‌ها، ترکیب پرتفوی، معیارهای ریسک) | `reg_no` |
| `fund_histories` | سری زمانی NAV هر صندوق (بک‌فیل + زنده) | `(fund_reg_no, observed_at)` منحصربه‌فرد |
| `etf_market` | تابلوی زنده ETFها (قیمت، NAV صدور/ابطال، پریمیوم) | `ins_code` |
| `etf_market_histories` | سری زمانی قیمت و NAV ETFها | `(ins_code, observed_at)` منحصربه‌فرد |
| `sync_status` | سلامت و آمار هر چرخه سینک (پوشش، امتیاز کیفیت) | `job_name` |
| `history_backfill_state` | آخرین زمان تلاش بک‌فیل هر صندوق (ضد حلقه بی‌نهایت) | `fund_reg_no` |
| `benchmark_histories` | سری زمانی شاخص کل بورس | `(benchmark_code, observed_at)` |
| `data_quality_issues` | تخلف‌های لایه اعتبارسنجی (قانون، شدت، جزئیات) | `(fund_reg_no, rule, observed_at)` |

طراحی کلیدی: **جداسازی «وضعیت لحظه‌ای» (`funds`) از «سری زمانی» (`fund_histories`)**. صفحه فهرست فقط از `funds` می‌خواند (سریع)، نمودارها از `fund_histories`. به‌روزرسانی زنده فقط ردیف `funds` و یک ردیف جدید در `fund_histories` را لمس می‌کند — با قید یکتایی `(fund_reg_no, observed_at)` که upsert را اتمیک و ایدمپوتنت می‌کند.

## ۱.۵ تصمیم‌های آگاهانه و محدودیت‌های فعلی

- **Migrationها به‌صورت اسکریپت SQL** در `migrations/` نگهداری می‌شوند و **خودکار** اعمال می‌شوند: هر دو سرویس web و worker قبل از شروع، `scripts/run_migrations.py` را اجرا می‌کنند (ردیاب `schema_migrations` + قفل `pg_advisory_lock` + تراکنش به ازای هر فایل — جزئیات در سند ۷). این ردیاب ساده عمداً به جای Alembic انتخاب شد؛ برای ۱۱ تغییر اسکیما در این بازه، شفاف‌ترین گزینه است.
- **جمع‌آوری شاخص کل (Benchmark)**: از `GetIndexB2History` با روش افزایشی (فقط مشاهدات جدیدتر از آخرین رکورد ذخیره‌شده) هر ۱۵ دقیقه sync می‌شود (`services/benchmark_sync.py`) و خوراک نمودار مقایسه با شاخص (سند ۵، نمودار ۸) و محاسبه Active Return است.
