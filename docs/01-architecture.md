# ۱. معماری سیستم

این سند نقشه کل سیستم است: چه چیزهایی کنار هم ایستاده‌اند، هرکدام چه کاری می‌کند، و چرا این‌طوری چیدمشان.

## نمای کلی

چهار سرویس دارم، هرکدام در کانتینر خودش:

- **`worker`** — فرآیند جمع‌آوری داده. چهار وظیفه زمان‌بندی‌شده دارد: سینک زنده صندوق‌های سهامی هر ۱ دقیقه، تابلوی معاملات ETF هر ۱ دقیقه، بک‌فیل تاریخچه هر ۱۰ ثانیه تا تکمیل، و سینک شاخص کل هر ۱۵ دقیقه؛ به‌علاوه جاروب دوره‌ای اعتبارسنجی.
- **`db`** — PostgreSQL 15، منبع حقیقت. همه‌چیز اینجا می‌نشیند.
- **`redis`** — کش مشترک بین web و worker.
- **`web`** — FastAPI، صفحات SSR و APIهای JSON. فقط می‌خواند و جواب می‌دهد؛ چیزی جمع نمی‌کند.

```
TSETMC API ──► worker ──► PostgreSQL ◄──► web (FastAPI) ──► مرورگر
                 │              ▲
                 ▼              │
              Redis (کش) ───────┘
```

جدا کردن web و worker یکی از مهم‌ترین تصمیم‌های اولیه بود و دلیلش ساده است: این دو چرخه عمر متفاوتی دارند. worker باید بی‌وقفه طبق زمان‌بند اجرا شود؛ web باید سبک بماند و به هر درخواست سریع جواب بدهد. اگر هر دو در یک فرآیند بودند، یک درخواست API کند می‌توانست سینک را عقب بیندازد و برعکس. جدا بودن یعنی هرکدام مستقل ری‌استارت و scale می‌شود. و Redis دقیقاً همین‌جا معنا پیدا می‌کند: وقتی worker داده را تازه می‌کند باید به web بگوید کش را دور بریزد — بدون یک نقطه هماهنگی مشترک، این گفتگو بین دو فرآیند ممکن نیست.

## الگوهای طراحی

### Repository

تمام دسترسی به دیتابیس — از upsert صندوق تا محاسبه معیارهای ریسک — در کلاس‌های Repository متمرکز است (`FundRepository`، `ETFRepository`، `BenchmarkRepository` در `core/repositories.py`). سرویس‌ها و روترها هیچ‌جا SQL نمی‌نویسند؛ اسم عملیات را صدا می‌زنند (`repo.upsert_fund_history(...)`). سودش مشخص است: کوئری‌ها یک نقطه تغییر دارند، در تست‌ها راحت mock می‌شوند، و اگر فردا دیتابیس عوض شود فقط همان یک لایه عوض می‌شود. برای عملیات حجیم از `INSERT ... ON CONFLICT` بومی Postgres استفاده می‌کنم — upsert اتمیک، به‌جای دور باطل read-modify-write که شرط مسابقه دارد.

### Provider

کلاینت منبع داده (`TSETMCProvider` در `services/providers.py`) تنها جایی است که آدرس‌ها، فرمت‌ها و رفتارهای عجیب API خارجی را می‌شناسد؛ از جمله retry با backoff و ایزوله‌سازی endpointهای ناپایدار. بقیه سیستم با یک دیکشنری تمیز کار می‌کند و اگر فردا منبع داده دومی اضافه شود، فقط یک Provider جدید می‌نویسم. اینجا یک درس برایم جا افتاد که قیمتش یک باگ نهفته بود: **قرارداد API خارجی باید از پاسخ واقعی استخراج شود، نه از حدس.** جایی که حدس زدم (شکل فیلدهای هویت ابزار)، باگ تا وقتی مسیرش فعال نشده بود خودش را نشان نداد — ماجرایش در فاز ۱۲ سند ۶ است.

### جداسازی نگرانی‌ها در services/

هر فایل در `services/` دقیقاً یک کار می‌کند: `providers` با دنیای بیرون حرف می‌زند، `preprocessing` تمیز می‌کند، `fund_sync` و `tasks` خط لوله را هماهنگ می‌کنند، `validation` اعتبارسنجی می‌کند، `analytics` و `risk` محاسبه می‌کنند. یک نکته عمدی: محاسبات مالی و قوانین اعتبارسنجی توابع **خالص** (pure) هستند — نه دیتابیس می‌بینند نه شبکه. برای همین با کمترین هزینه تست شدند، و این مهم است چون عدد مالیِ محاسبه‌شده باید اثبات‌پذیر درست باشد، نه «احتمالاً درست».

### مدارشکنی و تحمل خطا

هر وظیفه زمان‌بندی‌شده در `worker.py` داخل `try/except` مستقل است: شکست یک سینک، سرویس را نمی‌کشد. endpointهای ناپایدار TSETMC (که گاهی 500 تصادفی می‌دادند) از مسیر اصلی جدا شده‌اند تا کل مدار را مسموم نکنند؛ در صورت شکست، سیستم با آخرین داده معتبر ادامه می‌دهد و صندوق موردنظر برای تلاش مجدد در `history_backfill_state` می‌ماند.

## مدل داده

| جدول | محتوا | کلید |
|---|---|---|
| `funds` | اطلاعات پایه و فوری صندوق (NAV، بازدهی‌ها، ترکیب پرتفوی، معیارهای ریسک) | `reg_no` |
| `fund_histories` | سری زمانی NAV هر صندوق (بک‌فیل + زنده) | `(fund_reg_no, observed_at)` منحصربه‌فرد |
| `etf_market` | تابلوی زنده ETFها (قیمت، NAV صدور/ابطال، پریمیوم) | `ins_code` |
| `etf_market_histories` | سری زمانی قیمت و NAV ETFها | `(ins_code, observed_at)` منحصربه‌فرد |
| `sync_status` | سلامت و آمار هر چرخه سینک (پوشش، امتیاز کیفیت) | `job_name` |
| `history_backfill_state` | آخرین زمان تلاش بک‌فیل هر صندوق (ضد حلقه بی‌نهایت) | `fund_reg_no` |
| `benchmark_histories` | سری زمانی شاخص کل بورس | `(benchmark_code, observed_at)` |
| `data_quality_issues` | تخلف‌های لایه اعتبارسنجی (قانون، شدت، جزئیات) | `(fund_reg_no, rule, observed_at)` |
| `schema_migrations` | ردپای مهاجرت‌های SQL اعمال‌شده در بوت | `filename` |

یک تصمیم که از روز اول روشن بود: جدا کردن «وضعیت لحظه‌ای» (`funds`) از «سری زمانی» (`fund_histories`). صفحه فهرست فقط از `funds` می‌خواند و سریع است؛ نمودارها از `fund_histories`. سینک زنده فقط ردیف `funds` و یک ردیف جدید در `fund_histories` را لمس می‌کند — و قید یکتایی `(fund_reg_no, observed_at)` upsert را اتمیک و ایدمپوتنت می‌کند؛ اجرای دوباره همان چرخه، داده تکراری نمی‌سازد. به همین دلیل است که می‌توانم سینک را هر دقیقه بدون ترس اجرا کنم.

## تصمیم‌های آگاهانه و محدودیت‌های فعلی

- **مهاجرت‌ها اسکریپت SQL ساده در `migrations/` هستند و در بوت خودکار اعمال می‌شوند:** هر دو سرویس قبل از شروع، `scripts/run_migrations.py` را اجرا می‌کنند (ردیاب `schema_migrations` + قفل `pg_advisory_lock` + تراکنش به‌ازای هر فایل — جزئیات در سند ۷). Alembic را عمداً نیاوردم؛ برای ۱۱ تغییر اسکیما در این بازه، شفافیت اسکریپت ساده از قدرت یک ابزار سنگین مهم‌تر بود. قبل از تیم‌سازی، یک جابه‌جایی محلی است.
- **سینک شاخص کل افزایشی است:** `GetIndexB2History` همیشه کل تاریخچه از ۱۳۸۷ را برمی‌گرداند؛ با مقایسه با آخرین تاریخ ذخیره‌شده، هر چرخه فقط ۱-۲ ردیف جدید می‌نویسد. خوراک نمودار مقایسه با شاخص (سند ۵، نمودار ۸) و محاسبه Active Return است.
