# ۱. معماری سیستم

## ۱.۱ نمای کلی

سیستم از چهار سرویس مستقل تشکیل شده که هرکدام در کانتینر خودش اجرا می‌شود:

```
                         ┌────────────────────────────────────────┐
                         │              TSETMC API               │
                         │   (منبع رسمی داده بازار بورس ایران)     │
                         └──────────────┬─────────────────────────┘
                                        │ HTTPS (requests bulk + httpx async)
                         ┌──────────────▼─────────────────────────┐
                         │             worker (APScheduler)       │
                         │  • سینک زنده صندوق‌های سهامی (هر ۱ دقیقه)│
                         │  • تابلوی ETF زنده (هر ۱ دقیقه)         │
                         │  • بک‌فیل تاریخچه (بوت‌استرپ)           │
                         │  • سینک شاخص کل (هر ۱۵ دقیقه)           │
                         │  • جاروب اعتبارسنجی (هر ۱۵ دقیقه)       │
                         └───────┬───────────────────┬────────────┘
                                 │ SQLAlchemy        │
                    ┌────────────▼───────┐   ┌───────▼────────┐
                    │   PostgreSQL 15    │   │    Redis 7     │
                    │  (منبع حقیقت داده)  │   │ (کش + لایه داغ) │
                    └────────────▲───────┘   └───────▲────────┘
                                 │            invalidate │ cache
                    ┌────────────┴───────────────┐        │
                    │        web (FastAPI)       ├────────┘
                    │  • صفحات SSR (Jinja2)      │
                    │  • APIهای JSON تحلیلی      │
                    └────────────┬───────────────┘
                                 │ HTTP
                           ┌─────▼──────┐
                           │   مرورگر    │
                           │ Bootstrap  │
                           │ Chart.js + │
                           │ Highcharts │
                           └────────────┘
```

**چرا دو فرآیند جدا (`web` و `worker`)؟** جمع‌آوری داده و سرو کردن داده دو چرخه عمر متفاوت دارند. `worker` باید بدون وقفه طبق برنامه زمان‌بندی اجرا شود؛ `web` باید سبک بماند و به هر درخواست سریع جواب بدهد. اگر هر دو توی یک فرآیند بودند، یک درخواست API کند می‌توانست سینک را عقب بیندازد و برعکس. جدا کردنشان این اجازه را می‌دهد که هرکدام مستقل ری‌استارت یا scale شود.

## ۱.۳ الگوهای طراحی استفاده‌شده

### Repository Pattern (`core/repositories.py`)

تمام دسترسی به دیتابیس — از upsert صندوق تا محاسبه معیارهای ریسک — توی کلاس‌های Repository متمرکز است (`FundRepository`, `ETFRepository`, `BenchmarkRepository`). سرویس‌ها و روترها هیچ‌جا SQL نمی‌نویسند؛ معنی عملیات را صدا می‌زنند (`repo.upsert_fund_history(...)`). نتیجه‌اش این است که کوئری‌ها یک نقطه تغییر دارند، در تست‌ها راحت mock می‌شوند و منطق دامنه از جزئیات ذخیره‌سازی جدا می‌ماند — اگر فردا دیتابیس عوض شود، فقط Repository عوض می‌شود.

هر Repository یک `db: Session` می‌گیرد و برای هر عملیات یک متد صریح دارد. برای عملیات حجیم از `pg_insert` بومی PostgreSQL با `ON CONFLICT` استفاده می‌کنم — upsert اتمیک، بدون دور باطل read-modify-write.

### Provider Pattern (`services/providers.py`)

کلاینت منبع داده (`TSETMCProvider`) تنها جایی است که آدرس‌ها، فرمت‌ها و رفتارهای عجیب API خارجی را می‌شناسد — از جمله retry با backoff و ایزوله‌سازی endpointهای ناپایدار. بقیه سیستم همیشه با یک رابط تمیز و پایدار کار می‌کند و اگر فردا منبع داده دوم اضافه شود، فقط یک Provider جدید می‌نویسم. یک نکته‌ای که اینجا برایم جا افتاد: **قرارداد API خارجی باید از پاسخ واقعی استخراج شود، نه از حدس** — جایی که حدس زدم (شکل فیلدهای هویت ابزار)، یک باگ نهفته ساخت که فقط وقتی مسیرش فعال شد خودش را نشان داد (ماجرایش در سند ۶، فاز ۱۲).

### Separation of Concerns بین سرویس‌ها

هر فایل در `services/` دقیقاً یک نگرانی دارد:

| سرویس | نگرانی | خروجی |
|---|---|---|
| `providers` | ارتباط با دنیای بیرون | دیکشنری خام |
| `preprocessing` | پاک‌سازی داده خام | دیکشنری تمیز |
| `fund_sync` / `tasks` | هماهنگی خط لوله | ردیف‌های دیتابیس + امتیاز کیفیت |
| `validation` / `validation_sweep` | اعتبارسنجی صحت داده و قرنطینه | تخلف‌های ثبت‌شده |
| `benchmark_sync` / `history_bootstrap` | تکمیل داده از منبع (شاخص و تاریخچه) | ردیف‌های جدید |
| `analytics` / `risk` / `etf_analytics` | محاسبات مالی خالص | عدد/لیست |
| `data_quality` | سنجش سلامت داده | امتیاز/پوشش |

محاسبات مالی (`analytics`, `risk`) و قوانین اعتبارسنجی (`validation`) عمداً **خالص** (pure) هستند: نه دیتابیس می‌بینند نه شبکه. برای همین با کمترین تلاش تست شدند — و این مهم است، چون عدد مالیِ محاسبه‌شده باید اثبات‌پذیر درست باشد.

### Graceful Degradation و ایزوله‌سازی خطا

هر وظیفه زمان‌بندی‌شده در `worker.py` داخل `try/except` مستقل است: شکست یک سینک، سرویس را نمی‌کشد. endpointهای ناپایدار TSETMC (که گاهی 500 می‌دهند) از مسیر اصلی جدا شده‌اند تا «مدارشکن» کل سیستم را مسموم نکنند؛ در صورت شکست، سیستم با آخرین داده معتبر ادامه می‌دهد و صندوق موردنظر برای تلاش مجدد در صف می‌ماند (`history_backfill_state`).

## ۱.۴ مدل داده (اسکیما)

| جدول | محتوا | کلید |
|---|---|---|
| `funds` | اطلاعات پایه و فوری صندوق (NAV، بازدهی‌ها، ترکیب پرتفوی، معیارهای ریسک) | `reg_no` |
| `fund_histories` | سری زمانی NAV هر صندوق (بک‌فیل + زنده) | `(fund_reg_no, observed_at)` منحصربه‌فرد |
| `etf_market` | تابلوی زنده ETFها (قیمت، NAV صدور/ابطال، پریمیوم) | `ins_code` |
| `etf_market_histories` | سری زمانی قیمت و NAV ETFها | `(ins_code, observed_at)` منحصربه‌فرد |
| `sync_status` | سلامت و آمار هر چرخه سینک (پوشش، امتیاز کیفیت) | `job_name` |
| `history_backfill_state` | آخرین زمان تلاش بک‌فیل هر صندوق (ضد حلقه بی‌نهایت) | `fund_reg_no` |
| `benchmark_histories` | سری زمانی شاخص کل بورس | `(benchmark_code, observed_at)` |
| `data_quality_issues` | تخلف‌های لایه اعتبارسنجی (قانون، شدت، جزئیات) | `(fund_reg_no, rule, observed_at)` |
| `schema_migrations` | ردپای مهاجرت‌های SQL اعمال‌شده در بوت | `filename` |

طراحی کلیدی‌ای که از اول روشن بود: **جداسازی «وضعیت لحظه‌ای» (`funds`) از «سری زمانی» (`fund_histories`)**. صفحه فهرست فقط از `funds` می‌خواند (سریع)، نمودارها از `fund_histories`. به‌روزرسانی زنده فقط ردیف `funds` و یک ردیف جدید در `fund_histories` را لمس می‌کند — و قید یکتایی `(fund_reg_no, observed_at)` upsert را اتمیک و ایدمپوتنت می‌کند؛ یعنی اجرای دوباره همان چرخه، داده تکراری نمی‌سازد.

## ۱.۵ تصمیم‌های آگاهانه و محدودیت‌های فعلی

- **Migrationها به‌صورت اسکریپت SQL** در `migrations/` نگهداری می‌شوند و **خودکار** اعمال می‌شوند: هر دو سرویس web و worker قبل از شروع، `scripts/run_migrations.py` را اجرا می‌کنند (ردیاب `schema_migrations` + قفل `pg_advisory_lock` + تراکنش به ازای هر فایل — جزئیات در سند ۷). این ردیاب ساده را عمداً به جای Alembic انتخاب کردم؛ برای ۱۱ تغییر اسکیما در این بازه، شفاف‌ترین گزینه بود.
- **جمع‌آوری شاخص کل (Benchmark)**: از `GetIndexB2History` با روش افزایشی (فقط مشاهدات جدیدتر از آخرین رکورد ذخیره‌شده) هر ۱۵ دقیقه sync می‌شود (`services/benchmark_sync.py`) و خوراک نمودار مقایسه با شاخص (سند ۵، نمودار ۸) و محاسبه Active Return است.
