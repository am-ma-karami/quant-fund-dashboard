# ۷. استقرار و عملیات (Deployment & Operations)

## ۷.۱ پیش‌نیازها

| ابزار | نسخه | توضیح |
|---|---|---|
| Docker | 24+ | با Docker Compose v2 |
| دسترسی اینترنت | — | دسترسی به `cdn.tsetmc.com` برای دریافت داده و CDNها برای کتابخانه‌های نمودار |

**هیچ چیز دیگری لازم نیست** — نه Python روی میزبان، نه نصب دیتابیس. این دقیقاً خواسته تسک است: «به صورت مستقیم بر روی هر محیطی قابل اجرا». و من این جمله را جدی گرفتم: یک بار `docker compose down -v` زدم و سیستم را از صفر واقعی بالا آوردم — همان مسیری که ارزیاب می‌رود — تا مطمئن شوم «مستقیم» واقعاً مستقیم است. ماجرایش در فاز ۱۳ (سند ۶) است.

## ۷.۲ اجرا

```bash
# ۱. (اختیاری) کپی فایل پیکربندی — بدون آن هم compose از مقادیر پیش‌فرض استفاده می‌کند
cp .env.example .env

# ۲. ساخت تصویر و اجرای سرویس‌ها
docker compose up --build

# ۳. مشاهده وضعیت
docker compose ps
```

سرویس‌ها با `restart: unless-stopped` اجرا می‌شوند (بازگشت خودکار پس از ری‌استارت میزبان).

**اگر PyPI در دسترس نباشد** (برخی شبکه‌های ایران به `pypi.org` timeout می‌دهند — این را در اجرای واقعی همین پروژه تجربه کردم: ساخت تصویر وسط کار می‌مرد و همه سرویس‌ها پایین می‌آمدند): ساخت تصویر با آینه — پیش‌فرض در `Dockerfile` همچنان `pypi.org` است و آینه فقط هنگام build تزریق می‌شود:

```bash
docker compose build --build-arg PIP_INDEX_URL=https://pypi.tuna.tsinghua.edu.cn/simple
docker compose up
```

این آینه را در همین محیط راستی‌آزمایی کرده‌ام — بین چند گزینه داخلی و خارجی، تنها آینه‌ای بود که واقعاً جواب داد.

## ۷.۳ توپولوژی سرویس‌ها

| سرویس | تصویر | پورت | Health Check | وابستگی |
|---|---|---|---|---|
| `db` | `postgres:15` | 5432 (میزبان برای دیباگ) | `pg_isready` هر ۳ ثانیه | — |
| `redis` | `redis:7-alpine` | داخلی | `redis-cli ping` | — |
| `web` | build محلی | 8000 | `GET /health` هر ۱۰ ثانیه | سلامت db و redis |
| `worker` | build محلی | — | ندارد (لاگ‌محور) | سلامت db |

- **`depends_on: condition: service_healthy`**: وب و کارگر تا سالم‌شدن دیتابیس بالا نمی‌آیند — این همان رفع مشکل مسابقه راه‌اندازی فاز ۰ است؛ اولین باگی که در اولین اجرا دیدم و اولین commit امنیتی/زیرساختی را تولید کرد.
- **داده پایدار**: named volume های `postgres_data` و `redis_data` — بازسازی کانتینرها داده را پاک نمی‌کند.
- **استدلال پورت db روی میزبان**: برای دیباگ و اجرای اسکریپت‌های migration در محیط توسعه باز است؛ در استقرار تولیدی باید حذف شود. این را صریح می‌نویسم تا انتخاب، آگاهانه دیده شود نه تصادفی.

## ۷.۴ متغیرهای محیطی (`.env`)

| متغیر | نقش | مثال |
|---|---|---|
| `POSTGRES_USER` / `POSTGRES_PASSWORD` | اعتبارنامه دیتابیس | `quant_user` |
| `POSTGRES_DB` | نام دیتابیس | `fund_db` |
| `DATABASE_URL` | رشته اتصال سرویس‌ها (داخل compose تزریق می‌شود) | `postgresql://user:pass@db:5432/fund_db` |
| `REDIS_URL` | آدرس کش | `redis://redis:6379/0` |

هر سه متغیر در `docker-compose.yml` پیش‌فرض دارند (`quant_user` / `quant_password` / `fund_db`) — دقیقاً همان مقادیر fallback در `core/database.py` — بنابراین اجرا **بدون فایل `.env` هم ممکن است**. این هماهنگی عمدی بود: قبلاً compose فایل `.env` را اجباری می‌کرد در حالی که `.env.example` خالی بود — یعنی کلون تازه اصلاً بالا نمی‌آمد. حالا `.env` فقط برای override است (مثلاً استقرار تولیدی). فایل `.env` در `.gitignore` است (درس امنیتی فاز ۰)؛ `.env.example` الگوی آن است.

## ۷.۵ تغییرات اسکیما (Migrations)

پوشه `migrations/` شامل ۱۱ اسکریپت SQL به ترتیب شماره است. اعمال آن‌ها **کاملاً خودکار** است و هیچ قدم دستی لازم ندارد — این بخش را عمداً سخت‌سازی کردم تا «اجرای مستقیم روی هر محیطی» واقعاً مستقیم باشد:

- **ترتیب بوت:** هر دو سرویس web و worker با `ENTRYPOINT` مشترک (`scripts/entrypoint.sh`) شروع می‌شوند که پیش از شروع فرآیند، `scripts/run_migrations.py` را اجرا می‌کند. شکست مهاجرت = خروج غیرصفر و توقف بوت (سیاست restart دوباره تلاش می‌کند).
- **جدول‌های پایه:** از مدل‌های SQLAlchemy با `Base.metadata.create_all` ساخته می‌شوند؛ فایل‌های SQL فقط آن‌ها را گسترش می‌دهند (ایندکس، جدول‌های تکمیلی، اصلاح ستون).
- **ردیاب:** جدول `schema_migrations` ثبت می‌کند کدام فایل اعمال شده — هر فایل **دقیقاً یک‌بار** اجرا می‌شود، حتی با ری‌استارت‌های مکرر.
- **اتمی بودن هر فایل:** هر مهاجرت در تراکنش جداگانه است — یا کامل اعمال می‌شود یا هیچ‌چیز؛ با شکست، rollback و توقف.
- **مسابقه راه‌اندازی:** web و worker هم‌زمان روی دیتابیس خالی بوت می‌شوند؛ `pg_advisory_lock` تضمین می‌کند فقط یک فرآیند مهاجرت را اجرا کند و دیگری منتظر بماند. این را زنده دیده‌ام: روی ولوم تازه، worker هر ۱۱ مهاجرت را زد و web منتظر ماند تا تمام شود.
- **امنیت روی هر دو حالت اسکیما:** مهاجرت‌هایی که حالتی را اصلاح می‌کنند که `create_all` دیگر از ابتدا درست می‌سازد (مثل ۰۰۹: تبدیل `is_etf` رشته‌ای به boolean) با نگهبان `information_schema` نوشته شده‌اند — روی دیتابیس تازه (ستون از قبل boolean) و دیتابیس قدیمی (ستون متنی) هر دو امن هستند. همین مهاجرت را در راستی‌آزمایی بوت سرد روی دیتابیس تازه خطا داد و با نگهبان اصلاح کردم — مهاجرت‌ها هم مثل بقیه خط لوله، با اجرا روی داده واقعی سنجیده می‌شوند.
- **ایدمپوتنسی دو لایه:** خود فایل‌ها هم با `IF NOT EXISTS` نوشته شده‌اند؛ ردیاب لایه دوم است (ضمانت «یک‌بار»، مستقل از محتوای فایل).

اجرای دستی (فقط برای دیباگ):

```bash
docker exec quant-fund-dashboard-web-1 python scripts/run_migrations.py
```

- **محدودیت شناخته‌شده:** این ردیاب ساده (فقط forward، بدون downgrade) عمداً انتخاب شد — نه Alembic — چون در مقیاس فعلی شفاف‌ترین گزینه است؛ مهاجرت به Alembic قبل از تیم‌سازی یک تغییر محلی است.

## ۷.۶ مانیتورینگ و سلامت

| مسیر | محتوا |
|---|---|
| `GET /health` | سلامت فرآیند وب (برای Docker) |
| `GET /ready` | آمادگی سرویس (readiness) |
| `GET /api/health/data` | سلامت خط لوله داده: آخرین سینک، پوشش، امتیاز کیفیت، نرخ شکست |
| داشبورد → DATA QUALITY | نمایش زنده همان اطلاعات برای کاربر |
| داشبورد → HISTORY BACKFILL | پیشرفت تکمیل تاریخچه (تعداد رکوردها و صندوق‌های کامل) |
| `docker logs quant-fund-dashboard-worker-1` | لاگ‌های ساخت‌یافته کارگر (هر وظیفه، شروع/پایان/خطا) |

**چرا لاگ ساخت‌یافته؟** قالب ثابت `%(asctime)s - [%(levelname)s] - %(name)s : %(message)s` در همه فرآیندها — قابل grep و قابل جمع‌آوری توسط هر ابزار جمع‌آوری لاگ (ELK/Loki) در آینده. بخش عمده دیباگ‌های همین پروژه (حلقه بی‌نهایت بک‌فیل، تراکنش ۴۰ دقیقه‌ای) مستقیم از همین لاگ‌ها شروع شد.

## ۷.۷ مسیر ارتقا به محیط تولیدی (و Kubernetes)

شرح شغل آشنایی با Kubernetes را می‌خواهد؛ مسیر مهاجرت این معماری به K8s را از روز اول جلوی چشم داشتم و مستقیم است:

1. هر سرویس compose → یک Deployment + Service جدا.
2. `db` و `redis` → Managed services (مثلاً RDS/ElastiCache) یا StatefulSet با PVC.
3. Healthcheck های موجود مستقیماً به `livenessProbe` / `readinessProbe` تبدیل می‌شوند.
4. افزودن `replicas: 2+` برای `web` (بدون state) — معماری را عمداً stateless نگه داشته‌ام تا این مقیاس‌پذیری ممکن باشد.
5. اسرار (`DATABASE_URL`) → Secret های K8s به جای `.env`.

**چرا از روز اول K8s نه؟** برای یک محیط توسعه و ارزیابی، compose با یک فرمان اجرا می‌شود و همان توپولوژی را آموزش می‌دهد. K8s وقتی لازم است که تعداد نمونه‌ها و استقرار چندمحیطی مطرح شود — هزینه عملیاتی آن از همان ابتدا، انتخاب درستی نیست. این همان اصل «سادگی آگاهانه» سند ۲ است: زیرساخت باید با مقیاس واقعی مسئله بیاید، نه جلوتر از آن.
