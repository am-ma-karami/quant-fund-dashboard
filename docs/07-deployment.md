# ۷. استقرار و عملیات (Deployment & Operations)

## ۷.۱ پیش‌نیازها

| ابزار | نسخه | توضیح |
|---|---|---|
| Docker | 24+ | با Docker Compose v2 |
| دسترسی اینترنت | — | دسترسی به `cdn.tsetmc.com` برای دریافت داده و CDNها برای کتابخانه‌های نمودار |

**هیچ چیز دیگری لازم نیست** — نه Python روی میزبان، نه نصب دیتابیس. این دقیقاً خواسته تسک است: «به صورت مستقیم بر روی هر محیطی قابل اجرا».

## ۷.۲ اجرا

```bash
# ۱. کپی فایل پیکربندی
cp .env.example .env

# ۲. ساخت تصویر و اجرای سرویس‌ها
docker compose up --build

# ۳. مشاهده وضعیت
docker compose ps
```

سرویس‌ها با `restart: unless-stopped` اجرا می‌شوند (بازگشت خودکار پس از ری‌استارت میزبان).

## ۷.۳ توپولوژی سرویس‌ها

| سرویس | تصویر | پورت | Health Check | وابستگی |
|---|---|---|---|---|
| `db` | `postgres:15` | 5432 (میزبان برای دیباگ) | `pg_isready` هر ۳ ثانیه | — |
| `redis` | `redis:7-alpine` | داخلی | `redis-cli ping` | — |
| `web` | build محلی | 8000 | `GET /health` هر ۱۰ ثانیه | سلامت db و redis |
| `worker` | build محلی | — | ندارد (لاگ‌محور) | سلامت db |

- **`depends_on: condition: service_healthy`**: وب و کارگر تا سالم‌شدن دیتابیس بالا نمی‌آیند (رفع مشکل مسابقه راه‌اندازی در فاز ۰).
- **داده پایدار**: named volume های `postgres_data` و `redis_data` — بازسازی کانتینرها داده را پاک نمی‌کند.
- **استدلال پورت db روی میزبان**: برای دیباگ و اجرای اسکریپت‌های migration در محیط توسعه باز است؛ در استقرار تولیدی باید حذف شود.

## ۷.۴ متغیرهای محیطی (`.env`)

| متغیر | نقش | مثال |
|---|---|---|
| `POSTGRES_USER` / `POSTGRES_PASSWORD` | اعتبارنامه دیتابیس | `quant_user` |
| `POSTGRES_DB` | نام دیتابیس | `fund_db` |
| `DATABASE_URL` | رشته اتصال سرویس‌ها (داخل compose تزریق می‌شود) | `postgresql://user:pass@db:5432/fund_db` |
| `REDIS_URL` | آدرس کش | `redis://redis:6379/0` |

فایل `.env` در `.gitignore` است (درس امنیتی فاز ۰)؛ `.env.example` الگوی آن است.

## ۷.۵ تغییرات اسکیما (Migrations)

پوشه `migrations/` شامل اسکریپت‌های SQL به ترتیب شماره است (۹ اسکریپت تاکنون):

```bash
docker exec -i quant-fund-dashboard-db-1 psql -U quant_user -d fund_db < migrations/00N_name.sql
```

- هر اسکریپت **ایدمپوتنت** نوشته شده (`CREATE TABLE IF NOT EXISTS`، `ADD COLUMN IF NOT EXISTS`) تا اجرای تکراری بی‌ضرر باشد.
- جدول‌ها علاوه بر این در بوت هر فرآیند با `Base.metadata.create_all` ساخته می‌شوند (سازگاری برای محیط توسعه).
- **محدودیت شناخته‌شده:** ردیاب migration خودکار (Alembic) هنوز اضافه نشده؛ در مقیاس فعلی (یک توسعه‌دهنده، یک محیط) اسکریپت صریح ساده‌تر و قابل بازبینی است. قبل از تیم‌سازی، Alembic اولین آیتم است.

## ۷.۶ مانیتورینگ و سلامت

| مسیر | محتوا |
|---|---|
| `GET /health` | سلامت فرآیند وب (برای Docker) |
| `GET /ready` | آمادگی سرویس (readiness) |
| `GET /api/health/data` | سلامت خط لوله داده: آخرین سینک، پوشش، امتیاز کیفیت، نرخ شکست |
| داشبورد → DATA QUALITY | نمایش زنده همان اطلاعات برای کاربر |
| داشبورد → HISTORY BACKFILL | پیشرفت تکمیل تاریخچه (تعداد رکوردها و صندوق‌های کامل) |
| `docker logs quant-fund-dashboard-worker-1` | لاگ‌های ساخت‌یافته کارگر (هر وظیفه، شروع/پایان/خطا) |

**چرا لاگ ساخت‌یافته؟** قالب ثابت `%(asctime)s - [%(levelname)s] - %(name)s : %(message)s` در همه فرآیندها — قابل grep و قابل جمع‌آوری توسط هر ابزار جمع‌آوری لاگ (ELK/Loki) در آینده.

## ۷.۷ مسیر ارتقا به محیط تولیدی (و Kubernetes)

شرح شغل آشنایی با Kubernetes را می‌خواهد؛ مسیر مهاجرت این معماری به K8s مستقیم است:

1. هر سرویس compose → یک Deployment + Service جدا.
2. `db` و `redis` → Managed services (مثلاً RDS/ElastiCache) یا StatefulSet با PVC.
3. Healthcheck های موجود مستقیماً به `livenessProbe` / `readinessProbe` تبدیل می‌شوند.
4. افزودن `replicas: 2+` برای `web` (بدون state) — معماری فعلاً وب را stateless نگه داشته تا این مقیاس‌پذیری ممکن باشد.
5. اسرار (`DATABASE_URL`) → Secret های K8s به جای `.env`.

**چرا از روز اول K8s نه؟** برای یک محیط توسعه و ارزیابی، compose با یک فرمان اجرا می‌شود و همان توپولوژی را آموزش می‌دهد. K8s وقتی لازم است که تعداد نمونه‌ها و استقرار چندمحیطی مطرح شود — هزینه عملیاتی آن از همان ابتدا، انتخاب درستی نیست.
